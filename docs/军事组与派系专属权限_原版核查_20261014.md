# 军事组与派系专属权限：原版核查

2026-10-14。只读核查本机游戏 `data/db.pack`，未修改软件代码或游戏包。
使用当前随包 schema 和原生读表器；完整对照数据在 `.tmp/permission-study/exclusive_vanilla.csv`。

> 后续实现 v1.5.15：归属同时认军事组与 allowed=true，原版两类许可保留并提示无法取消。
> 种族添加授权全部所属军事组，派系添加只写专属表；通用入口已取消并入种族。
> 移除支持专属许可、军事组、全部三个渠道，限定当前范围，专属许可不扩散到共享组的其他派系。
> 当前 MOD 已给下方例举的次元闪电炮精英补了军事组，因此原版单渠道例子不能直接当作该 MOD 的合并结果。

## 结论

`units_to_exclusive_faction_permissions_tables` 是用户提到的派系专属权限表。
它直接连接主单位和派系，可以在共享军事组的派系之间添加不同的单位许可。
创建派系专属的新单位时，公共单位继续使用军事组，专属单位使用目标派系的正向权限，
避免又把专属单位授权到大家共用的军事组。

## 两条关系

| 表 | 关系与身份 |
|---|---|
| `factions_tables` | 派系 key → military_group |
| `units_to_groupings_military_permissions_tables` | 单位 unit → military_group；真实身份 (unit, military_group) |
| `units_to_exclusive_faction_permissions_tables` | 单位 key → faction，带 allowed；真实身份 (key, faction) |

exclusive 表的 key 就是 `main_units_tables.unit`，不能另造权限记录名。
前一条按组授予，所有引用该组的派系共享；后一条按具体派系授予，不要求修改 factions 的军事组。
权限并不自动创建建筑、精英池或战帮升级路线等使用入口。

## 当前原版数据

军事组授权 5343 条；派系专属权限 1489 条，其中 true=1473、false=16。

| exclusive 状态 | 对应派系军事组是否也授权该单位 | 行数 |
|---|---|---:|
| true | 是 | 634 |
| true | 否 | 839 |
| false | 是 | 16 |

原版实例：

- `wh2_dlc12_skv_art_warp_lightning_cannon_ror_0` 对 `wh2_dlc09_skv_clan_rictus` 有 exclusive=true，
  而没有该单位对这个派系的军事组 `wh2_main_skv` 的匹配授权。
- `wh2_dlc16_wef_cav_great_stag_knights_ror_0` 对多家木精派系分别使用 exclusive=true，
  包括使用 `wh_dlc05_group_wood_elves` 的派系，以及使用 `wh2_dlc16_group_drycha` 的 `wh2_dlc16_wef_drycha`。
- 原版有 16 条 false 与军事组正向权限同时存在，均落到 `wh3_dlc21_wef_spirits_of_shanlin`；
  例如 `wh_dlc05_wef_inf_eternal_guard_0`，派系军事组为 `wh_dlc05_group_wood_elves`。

前三组计数与实例只证明数据库中同时配置了这些关系，不是本轮游戏引擎运行测试。
尤其不能仅凭 false 与军事组同时存在，就证明 false 一定覆盖军事组，或一定不覆盖。
项目现行规范将 false 视为不授予/撤销专属渠道，不作为覆盖其他渠道的通用黑名单；
如果需要对原版公共单位做派系级禁止，应单独做游戏内优先级测试，再决定实现。

## 共享军事组下配置不同新单位

### 两个已核对全部表记录的具体样例

官方中文名来自本机原版 `local_cn.pack`，两表记录来自 `db.pack`：

| 单位 | 军事组表全部记录 | 派系专属表 |
|---|---|---|
| 猛毒炮阵（瘟疫利爪投石机），`wh3_dlc29_skv_art_plagueclaw_catapult_ror` | `wh2_main_skv`、`wh2_main_skv_ikit`、`wh3_dlc29_group_endgame_skaven` | 7 个鼠人派系的 allowed=true，包括 `wh2_main_skv_clan_mors` |
| 伊克特的嗞杀炮（次元闪电炮），`wh2_dlc12_skv_art_warp_lightning_cannon_ror_0` | **整个军事组表中没有该单位记录** | 同样有 7 个鼠人派系的 allowed=true，包括 `wh2_main_skv_clan_mors` |

摩斯氏族的军事组为 `wh2_main_skv`。第一个单位对摩斯氏族有军事组与派系两条正向许可，
第二个没有任何军事组许可而具有派系正向许可；这解释了专属授权单位仍可能显示军事组蓝标。
完整目标核对输出：`.tmp/permission-study/target_result.log`。

以 A、B 共用军事组 G 为例：

| 单位 | 军事组 G 的授权 | 派系专属授权 |
|---|---|---|
| 公共单位 | 有 | 通常不需要 |
| A 的专属新单位 | 不添加到 G | key=该单位，faction=A，allowed=true |
| B 的专属新单位 | 不添加到 G | key=该单位，faction=B，allowed=true |
| A、B 共享的特殊单位 | 可不添加到 G | 分别向 A、B 添加 true |

这里不应把“只给 A 一条 true”理解成会自动撤销单位在公共军事组的已有许可。
若原版已经通过公共组授予，删除 MOD 自己的行也删除不了原版许可。
原版基础单位的排除与新单位的专属增补是两种任务。

## 核查时 v1.5.13 的角标与编辑入口（历史记录）

- 蓝色：没有任何军事组分配。
- 黄色：有其他军事组，但不满足当前种族/通用/派系所要求的军事组。
- 两者目前只表达军事组关系，不表达完整的派系可用性；即使 exclusive=true，也仍可能显示蓝色或黄色。
- 当前兵种库已经读取 exclusive=true，与军事组授权等来源组成单位集合；角标专门使用军事组快照。
- 当前“加入当前军事组”写军事组表。多个派系共用该组时，这是共享授权，不能表达只给一家的专属许可。
- 加兵进画布后还会自动调用 GrantUnit，因此要做专属单位工作流，需增加派系专属模式，避免自动补公共组。

合理的后续 UI 应同时显示“军事组分配”和“当前派系专属许可”，并提供分别编辑的入口；
蓝/黄色不再被解释为“该派系一定不能用”。本轮仅做调查，没有擅自改变上一轮用户确认的角标规则。
