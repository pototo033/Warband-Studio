## P1：优先修复

### 1. 同一个 PackArchive 并发读取会串字节（已复现）

入口：`src/WarbandStudio.Packfile/PackArchive.cs:147`。
`ReadRaw` 共用 FileStream，先设置 Position 再 Read，没有将整个读取过程同步。
视图模型在后台 Task.Run 读取派系、兵种库、表和导出，界面线程同时也可能读取画布与成本。
线程之间改写流位置时，一个条目会读到另一个条目的内容，或读到 EOF。

探针创建两个内容不同的 256 KiB 条目，共用一个 PackArchive 并行读取 1000 次：
一次运行出现 **475 次异常或字节不符**。该数字是本次压力测试结果，不是实际用户故障率。

建议：使用按文件偏移读取的 RandomAccess.Read，或锁住完整的定位与读满过程；
同时明确 Dispose 与在途读取的生命周期，导出前固定会话和编辑快照。
回归：同包并发读多条目必须逐字节一致；读取期间切包/关包不能污染新会话。

### 2. 切换工程没有隔离旧工程的会话（代码路径确认）

入口：`src/WarbandStudio.Ui/ViewModels/MainViewModel.Projects.cs:84`。
工程切换只处理未保存编辑，然后替换 `_projectDir`、Project 和全局 Backend.ProjectKey，
没有关闭或移除旧工程的包与画布。打开空工程时，旧包尤其可能继续成为当前包。
切回旧包编辑时，导出又从全局 ProjectKey 获取落表前缀，可能用新工程的 key 写旧工程包。

建议：切工程时先建立可验证的新工程状态，再关闭旧工程会话并清理画布、缓存与筛选；
或显式支持多工程，但每个会话独立持有工程归属和 key，不能共用全局 key。
回归：A 有包 → 打开空 B；A → B → 再编辑 A，包归属与落表 key 必须一致。

### 3. 历史还原前的备份清理可能删掉所选版本（已复现）

入口：`src/WarbandStudio.Ui/Services/Backend.cs:2139`；
清理：`src/WarbandStudio.Pack/ProjectStore.cs:186`。
还原先 BackupPack，BackupPack 新增备份后立即 PruneHistory，再 File.Copy 所选 backupFile。
达到保留上限时，选中的最旧备份可能已被清理，导致还原失败并失去那个历史版本。

探针设置 keep=1，创建一个旧备份，再运行实际 BackupPack：旧备份被删除，新备份存在。
默认 keep=20 达到上限后选择最旧版本也有同样条件。

建议：先把所选版本读取或复制到独立临时位置，再备份和替换；清理时保护当前还原源。
回归：满 20 份时还原最旧版本，原版本和还原前当前包均需保留到操作成功。

### 4. 连续修改成本资源会留下旧关联，清空资源也无效（已复现）

入口：`src/WarbandStudio.Ui/Services/Backend.Costs.cs:319`。
UpdateWarbandCost 只添加 RemovePoolCost 和新 PoolCosts，没有移除本轮该成本已有的 PoolCosts。
连续把资源 A 换成 B 后，两种资源都在待写列表；再清空资源，列表仍有两条。
CostList 只显示最后一条，导出却按组合键保留两种池关联，造成预览与落表不一致。

探针调用实际 Backend.UpdateWarbandCost：食物 → 骑士道 → 清空，待写关联数依次为 1/2/2。
落表对应 `src/WarbandStudio.Pack/WarbandAmender.cs:581`，所有 PoolCosts 均参与新增。

建议：更改资源前，清除该 costId 本轮旧关联，再写最终状态；保留不修改资源时的多资源原数据。
回归：创建→改资源、改资源→清空、改数量→再改数量、删→再加，最终导出只保留目标状态。

### 5. 保存不是原子替换，备份失败仍继续删除原包（代码路径确认）

入口：`src/WarbandStudio.Ui/Services/Backend.cs:2120`。
SaveInPlaceAsync 先 File.Delete(pack)，再 File.Move(tmp, pack)；两步间若中断或移动失败，
原路径会消失。备份异常或 BackupPack 返回 null 也不会终止保存。
`.saving` 可能仍可恢复，但普通打开工程不会把它当作工作包，用户容易误以为包丢失。

建议：临时文件写完并验证后采用同卷原子替换；重要备份失败时保留原包并报告失败；
保存失败恢复会话和编辑状态，明确临时文件恢复入口。
回归：模拟备份失败、替换失败、文件占用，原包始终可读且未保存编辑不丢。

### 6. 删除正在使用的成本会留下悬空引用（代码路径确认）

入口：`src/WarbandStudio.Ui/Services/Backend.Costs.cs:339`。
删除只处理成本行及资源关联，没有检查或迁移升级路线对 costId 的引用；
UI 的确认框也只说明删除两类行。若删除包内独有且正在使用的成本，路线会引用不存在的 id。

建议：先列出引用者，默认拒绝删除仍在使用的成本；提供明确的替代成本操作。
对普通 MOD 包还需覆盖其他消费表，不应只检查战帮路线。
回归：已有路线使用自建成本 → 删除成本，不能产生不存在的 resource_cost 引用。

## 优化空间

1. **按包绑定的异步任务**：派系/兵种/表读取在开始时抓取会话与版本；完成时校验包路径、版本和筛选条件。
   现有代数号只保护部分刷新入口，不能代替会话隔离与线程安全。
2. **成本清单缓存与异步加载**：CostList 与 PooledResources 多次打开和解码原版表、同步解析图标；
   可按 schema/游戏目录/包修订号缓存索引，再异步生成 UI 数据。
3. **多资源成本模型**：WarbandCost 只存一个池，而游戏允许一成本对应多资源；当前字典也会用后行覆盖前行。
   应显示资源列表，不能让“只改一个数量”悄悄清掉其他资源关联。
4. **统一编辑事务**：集中处理快照、编辑、缓存失效、UI 刷新、自动保存，避免各功能漏做其中一步。
   三态回归需要覆盖最终导出数据，而不仅是编辑后首次预览。
5. **按来源管理缓存**：本地化只往全局字典叠加，关闭包不撤掉其覆盖；应保留原版基底和每包图层，
   按当前包与参考包重新合成。图标、军事组和页签归属也采用同样的显式修订机制。
6. **保存与更新状态分开**：后台检查更新直接覆盖底栏 Status，可能盖住保存结果或编辑提示；
   更新提示可独立显示，保留主任务状态。

## 建议修复顺序

共享文件读取 → 原子保存/历史还原 → 工程隔离与会话恢复 → 成本连续编辑/引用保护 → 配置与错误传播 → 性能和模块优化。
前四类修复前，不建议把 v1.5.11 当作已排除数据风险的版本发布。
