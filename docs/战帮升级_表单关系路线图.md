## 二、页签归属推导链（严格按表单，不做近似）

页签属于哪些种族/派系，是**沿着这条链取并集**，每一步都是表单里的键：

```
页签 key
  └─ unit_upgrade_group_ui_infos_tables.category
       └─ 组 unit_upgrade_group
            └─ unit_to_unit_group_junctions_tables（组 → 兵）
                 └─ 兵 main_units.unit
                      └─ 这个兵能被哪些派系用
                           · factions_tables.military_group ↔ units_to_groupings_military_permissions_tables（主路）
                           · units_to_exclusive_faction_permissions_tables（allowed = true）
                           · building_units_allowed_tables（faction + enabled = true）
                                └─ 派系 factions_tables.key
                                     └─ 种族 factions_tables.subculture（_pro_sc_ 并回 _sc_）
```

**结论**：一个页签可以同时属于多个种族（混沌勇士与四神共用页签就是这么来的）。
工具里的 `pageRaces` / `pageFactions` 都是**数组**（并集），不是单选值。

## 四、当前授权与画布语义（v1.5.15）

1. **新建页签默认归当前种族/派系**
   - 种族级（右侧没点开具体派系）→ 给该种族**所有军事组**写授权；
   - 派系级（点开了具体派系）→ 只写该派系的 `units_to_exclusive_faction_permissions_tables`，`key=单位`、`faction=派系`、`allowed=true`。
2. **「打开页签」按钮**：可以把**别的种族的页签**也加进当前画布。
   打开行为本身不写两类授权；当前页签单位始终显示，只有当前范围缺权的单位打角标。
   悬浮显示军事组、专属许可和当前授权来源。
3. **右键菜单（组级）**：
   - 「添加归属」→ 种族填全部军事组，具体派系填专属许可；
   - 「移除归属」→ 明确选军事组、专属许可或全部，按当前范围删当前包对应组合键；原版两类许可无法取消；
   - 派系选择下移除军事组会影响共享该组的其他派系，面板明确提示。
4. **种族/派系下的页签列表**：归属与可见性分离；种族包含非传奇与共享军事组单位，不再设置通用入口。
5. **同一单位允许属于多个组、页签和画布**（v1.5.12，2026-10-13 用户更新规则）：
   加兵只新增目标组的 `unit_to_unit_group_junctions_tables` 关系，保留其他组里的关系；不再弹重复确认或覆盖旧位置。
   同一 `(unit, unit_group)` 关系仍去重，删除只针对目标组；读表仍必须拼接读。

## 五、工具里的读表铁律（血泪版）

1. `unit_to_unit_group_junctions_tables`、`unit_upgrade_group_ui_links_tables`、`unit_upgrade_to_unit_groups_tables`
   这三张表**键不唯一**，必须**拼接读**（`TableFiles.ReadConcat`）；按键合并会静默吃掉行（实测连线 751→641）。
2. 删行只能改**原文件**（覆盖表删不掉别人的行）；已有行的改值优先**就地改**（避免两份数据抢同一个 key）；
   **新增行按"这一行属于谁"落文件**（v1.5.9，见 §六）：
   · 页签内容表（组 / 兵↔组 / 坐标 / 连线 / 路线）→ `db/<表>/<项目key>_Upgrade_<页签key>`
     （和 MOD 作者那边的按种族文件同一族；一个页签一套；跨页路线跟 base 端；定不了页签的落 `..._Upgrade_其他`）；
   · 页签本体 / 授权 / 成本 → `db/<表>/zzzz_studio_edits`（跨页签共用、不归属单个页签；
     **名字排最后**——同一张表多文件按文件名加载顺序定胜负，`studio_*` 这样的名字会被 `Yukino_*` 顶掉）。
   目标文件跟包里已有的名字**只差大小写**时（`Yukino_Upgrade_Skv` vs 页签 SKV 该有的 `Yukino_Upgrade_SKV`）
   **并进那一份、沿用原件拼写**，绝不造大小写孪生文件。
3. 一切"归属"必须能沿本图找到依据；找不到依据先问用户，不猜。
4. **跨页的升级关系只改路线表**：两端组不在同一 `category` 时，只写 `unit_upgrade_to_unit_groups_tables`，
   **不写 `unit_upgrade_group_ui_links_tables`**（游戏按页签画坐标层，跨页的箭头画不出来；正常可见的箭头都同页）。
   「查看已有升级」面板与连接建线都按这条走；同页且已有连线的行才"路线 + 连线一起动"。
5. **一次导出内部的编辑按顺序叠加**：任何一步读表都**本轮缓冲优先**（`WarbandAmender.CurrentBytes`），
   要处理的文件清单 = 原包里的 + 本轮新写的（`TablePaths`）；键表同 key **后写为准**。
   不然"先加后删""先重命名后建页签"会互相覆盖（v0.85 修，见交接文档 §7.5）。
6. **军事组授权 / 专属授权按"组合键"合并**：`units_to_groupings_military_permissions_tables` 的真实身份是
   **(unit, military_group)**、`units_to_exclusive_faction_permissions_tables` 是 **(key, faction)** ——
   schema 的键列只标了第一列。用 `ReadMerged` + `Merge`（按键列）时，**本包的行会顶掉原版同一个兵的那一行**
   （实测：原版 5340 + 雪乃 382 → 按键合并 5394 行 vs 组合键 5531 行）。
   读这两张表用 `TableFiles.ReadComposite` + `MergeComposite`，口径 = **原版为基底 + 本包新增/覆盖重复**
   （v0.89 修，验收 ①b 盯着，见交接文档 §7.10）。


## 六、新增行的落表命名（v1.5.9 起）

### v1.7.7 当前规则（优先于下方历史自动命名规则）

v1.7.9 页签复制：将当前有效的组、兵↔组、坐标、页内路线和连线按原始字段快照，粘贴时组 key、upgrade_key 重新生成，其他参数保留。科技/建筑要求同步映射新 upgrade_key，新行写 `zzzz_studio_edits`；五张内容表仍使用目标页签实际归属与手填文件名。成本引用共用，军事组/专属许可、精英解锁和来源页签可见派系名单不复制。跨页路线跳过，复制不写包，粘贴整批可撤销。

- 创建／重命名页签同时填写完整落表文件名（例如 `EMP_n` 或 `Yukino_Upgrade_Emp_III`，不含目录或扩展名），可手动修改，禁止以数字结尾。
- 显式设置保存在 Pack 的 `warband_studio/tab_files.json`，只在用户编辑保存时写入；旧工程与旧缓存不需要此字段。
- 未显式设置时，以五张表内实际组→infos.category 归属优先复用作者文件；`EMP2`、`EMP_II`，以及 `EMP_III`、`EMPIII` 可辅助匹配，保留作者拼写。文件内容归属优先于名称猜测。
- 本表无文件时参考同页签其他四表；多个候选不猜，保存停止并要求用户在重命名页签中指定。没有任何候选的旧调用才使用下面的兼容自动命名。
- 用户修改文件名时，迁移该页签独占文件；跨页共享文件保留，新增内容使用指定文件。目标属于其他页签或同键内容冲突则拒绝保存，保留原包与编辑。
- 旧恢复缓存中尚未存在于原包的重复命名文件，按组合键归并到唯一作者原文件；待保存值优先，撤销重做状态同步规范化。已在作者原包中的文件不自动删除或改名。
- 打开、浏览、无编辑读表不执行写包，空编辑读表也不调用迁移、自愈或落表预览；恢复未保存修改与磁盘已有文件必须区分。

**规则**（用户口径，参考 MOD 作者那边的文件布局）：页签内容表的新行写进
`db/<表>/<项目key>_Upgrade_<页签key>`（项目 key = 工程 `project.json` 里的 `ProjectKey`；空 = `studio`）。

| 表 | 落法 |
|---|---|
| 组 / 兵↔组 / 坐标 / 连线 / 路线 | `<项目key>_Upgrade_<页签key>`（**一个页签一套文件**） |
| 页签本体（categories） / 授权 / 成本 | `zzzz_studio_edits` 单文件（跨页签共用，不归属单个页签） |
| 精英解锁（main_units） | `zzzz_studio_elite_unlock`（不变） |

- **页签怎么定**（`TabResolver`）：① 本会话编辑里的 category；② 包里 infos 行的 category；
  ③ 名字兜底 `<项目key>_<X>_…` 且 X 是已存在的页签 key。都认不出 → `..._Upgrade_其他`。
- **跨页路线**跟 `base_unit_group` 那一端走（用户定的）；连线本来就不跨页。
- **大小写归并**：目标名字跟包里已有的文件只差大小写（`Yukino_Upgrade_SKV` vs 作者的
  `Yukino_Upgrade_Skv`）→ **并进已有那一份、沿用它的拼写**（跳过归并会造出大小写孪生文件，
  游戏按文件名加载，谁赢说不准）。实现见 `WarbandStudio.Pack/TabFileNaming.cs`。
- **文件名结尾的数字换成字母**（RPFM 体检「Table name ends in number」：db 表文件名以数字结尾会触发一个
  "只有做它的人不崩、别人一进就崩"的怪问题）：**1=A、2=B、…、9=I、0=J**，结尾连续多个数字整段换
  （`MOD12`→`MODAB`）。例：页签 `SKV2` 的文件叫 `Yukino_Upgrade_SKVB`、`EMP3` → `Yukino_Upgrade_EMPC`、
  `VMP1` → `Yukino_Upgrade_VMPA`。**只动文件名**——页签 key / 组名 / 图名都保持原样。
  存量包的改名：`probe fix-table-names <pack> [out.pack] [--dry-run]`（纯改名、内容一字不动；
  目标名被占用会跳过并报告）。
- **一次性迁移**（把老 zzzz 覆盖表拆进新名字）：`probe tab-split <pack> [out.pack] --key <项目key> [--drop <包内路径>]… [--dry-run]`
  —— 只处理上表前五行；搬空的 zzzz 文件删掉；跑完会逐表校验"迁移前后身份键集合一致"。
  真实数据踩过的坑：**迁移前先确认工具/游戏没开着那个包**（文件锁），并且先 `--dry-run` 看一遍计划。


## 七、成本编辑与缓存（v1.6.1）

v1.6.5 补充：合并组不继承参与组任何升级或连线；删除路线同时清理
`unit_upgrade_to_tech_requirements` 和 `unit_upgrade_to_building_level_requirements` 对该路线的引用，

一个 resource_cost 可以通过多条 `resource_cost_pooled_resource_junctions` 对应多个资源池；
关联以 `pooled_resource_factor + resource_cost` 为组合键完整读取、合并和编辑。
成本表单选择一条资源关联修改数量/资源时，只改变该关联；其他关联及其 context/ui 保留。
清空只移除选中关联，追加则保留全部已有行；改值就地写作者文件，新增仍落 `zzzz_studio_edits`。
删除成本先按 schema 外键检查本包所有消费表及待写路线，仍有引用时拒绝；
重命名会迁移战帮路线，其他消费表还有引用时先拒绝，避免生成悬空引用。

成本基础表按包实例、schema 和原版 DB 文件版本缓存，预览按编辑修订缓存；切包、保存、撤销、还原、换游戏目录均失效。
全部编辑通过事务快照支持撤销重做；原生保存前先完成临时包校验和备份，再原子替换。

## 八、科技解锁挂在升级路线（2026-10-20 原版核对）

直接读取当前游戏 `data/db.pack`，不是以旧 AK 空表为依据：

- `unit_upgrade_to_tech_requirements_tables.technology` → `technologies_tables.key`。
- `unit_upgrade_to_tech_requirements_tables.unit_upgrade` → `unit_upgrade_to_unit_groups_tables.upgrade_key`。
- 路线再通过 `base_unit_group` / `target_unit_group` 指向两端兵组；`unit_to_unit_group_junctions_tables` 才决定组内兵种。
- 科技要求表是 `(technology, unit_upgrade)` 组合键；同一科技可以用于多条路线，不能只按 technology 合并丢行。

原版例子：`wh3_dlc20_chs_warriors_und_to_chosen` 从 `wh3_dlc20_chs_warriors_und` 升到 `wh3_dlc20_chs_chosen_und`，要求等级 7、扣除等级 7，并在科技要求表引用 `wh3_dlc20_chs_und_shared_chosen`。
同一目标神选者组另有 `wh3_dlc20_chs_chosen_und_to_self` 换武器路线（两端都是 chosen_und，等级 0/0），科技要求表没有为这条路线配置科技。这说明要求不随神选者单位或神选者兵组一概全局绑定。

因此同一兵种放进不同兵组/面板时，可为各自独立 upgrade_key 的路线配置不同科技；共享同一个 upgrade_key 才共享该路线的科技要求。这里只说明原版关联粒度，不推断多科技行在不同派系下的适用过滤/逻辑，也不把普通招募许可等同战帮升级科技。

原版 UI 源码 `源码/战锤9.0/ui/campaign ui/warband_upgrades.twui.xml` 的科技列表上下文为 `CcoCampaignUnitGroupUpgrade.TechRequirementsList`，与路线级关联一致。此次只读查询，未修改软件或 Pack。
